# packages/run

[English](README.md) | 中文

## 概述

run 分组回答关于"一份 harness 工作"的四个问题：它**是什么**（一个 Run，带封闭的生命周期与仅可追加的事件日志）、此刻**归谁所有**（一份租约，其 epoch 由每一次状态写入出示）、它被**要求做什么**（一份可追溯回用户目标的已编译任务画像），以及进程死亡时工作与消息**如何存活**（已领取任务与已提交未投递消息的持久化存储）。该分组可选且仅在宿主侧：它不注册工具、不注入提示词，这里没有任何东西会进入模型请求——模型能观察到的只是它那一轮是否跑了，而不是这些记账。当不止一个宿主可能争抢同一份工作，或崩溃不得丢失、也不得重复一次副作用时挂载它；单进程组合可以整组省略。

<a id="packages"></a>
## 包

| 包 | 角色 | ctx 键 |
|---|---|---|
| `run` | Run 的十状态生命周期、仅可追加的事件日志、持久化注册表，以及按 agent 会话开启 Run 的挂载插件 | `ctx.runs` |
| `task-profile` | 通用的已编译任务画像：目标引用、各自携带来源与置信度的约束，以及编译时选择提问而非猜测所产生的问题 | —（一个库；一个纯编译函数） |
| `lease` | 权威模型——按工作项的 epoch、每次状态写入出示的 fencing token、回收判据——以及内存版 provider | `ctx.leaseStore` |
| `lease-sqlite` | 持久化租约 provider：获取由 `BEGIN IMMEDIATE` 串行化，因此两个进程争抢同一工作项时不可能同时持有 | `ctx.leaseStore` |
| `message-bus` | 有效一次的副作用交接：outbox 使已提交的消息永不丢失，inbox 使丢失的确认不会带来第二次副作用，外加定向 mailbox 投递 | —（记录状态与决策函数） |
| `taskboard-sqlite` | 持久化任务板：领取由 `BEGIN IMMEDIATE` 串行化，因此两个进程争抢同一任务时不可能同时持有 | `ctx.taskStore` |

每个包自己的 README 位于下一层目录,目前只有英文版,这也是上面那些名字没有做成链接的原因:否则本页就会声称存在一个并不存在的中文对应页。

租约是这个分组的承重思想，也是那两个 SQLite 包看起来相似的原因。权威是**存储签发的一个 epoch**，从不是时间戳、也从不是调用方自选的数字，于是"我的租约过期了吗？"与"是否已被别人拿走？"成为同一个问题——问存储，而不是问两个宿主无法就其达成一致的时钟。

<a id="what-is-not-arrived-yet"></a>
## 尚未抵达的部分

记在这里，是因为本分组的各 README 所描述的契约，有些只被生产代码部分触及；把散文与运行中的系统对照的读者应当知道哪些是哪些。

- **生产中一个 Run 只占据两个状态，而非十个。** `ctx.runs` 在 `accepted` 开启 Run，挂载插件驱动的唯一一次转移是 `accepted → planning`，它点名为该 agent 首个模型步骤编译出的任务画像。往后直到终态的那些转移已实现、且非法时会被拒绝，但尚无任何生产调用方到达它们。
- **workflow 执行未被记入 Run 的日志。** 这类引用所需的 brand 已对齐；没有任何监听器追加过一条。
- **没有任何东西读回任务画像。** 它被编译、被追加到会话日志、并在 Run 的转移中被点名；把它放进模型请求属于后续 epic——这也正是它的校验先于它的读取方存在的原因。

<a id="dev-note"></a>
## 开发备注

<details>
<summary>面向维护者的工作上下文——点击展开</summary>

本开发备注是面向维护者的工作上下文：开放问题与尚未定下的方向。它明确不具权威性——已发布的行为与边界位于上面各节以及每个包自己的 README 中。

本分组尚未定下的开放问题是 **Run 的事件日志该存在哪里**。`run` 把它放在自己的存储文档里，会话日志中没有任何东西引用它；`task-profile` 把画像的**正文**放进会话日志，并让 Run 的日志按摘要引用它。两种答案都站得住，而本分组当前每种各持一份。让这件事成为有意而非偶然的，是归属判据——一份画像是从某个会话日志中的一条消息编译出来的，离开那个会话便没有意义，而一个 Run 可以跨越多个会话——但这条判据只写在这里，没有写进任何决策记录。

第二个问题是 **Run 在实践中是否可以跨会话**。类型面说一个 Run 可以承载多个会话，注册表也有对应操作；挂载插件却按会话铸造一个新的 Run，从不调用它，因此今天一个 subagent 拿到的是自己的 Run，而不是加入父级的 Run。那是正确的产品答案，还是一条未完成的 seam，尚未决定。

</details>
