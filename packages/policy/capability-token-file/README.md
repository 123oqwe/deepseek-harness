# @deepseek-ai/dsh-capability-token-file

## Summary

`dsh-capability-token-file` is the provider that makes [`@deepseek-ai/dsh-capability-token`](../capability-token/README.md) reachable. The definition package decides what a token IS and what narrowing is legal; this package mounts on a profile, issues one, and enforces it.

`src/index.ts` is the plugin: it restores the store, issues a session-root token at `agent/session-start`, arms `tools.requireCapabilityToken()` when the profile asks, and publishes itself as `ctx.capabilityTokens`. `src/store.ts` is the durability seam. `tests/provider.spec.ts` covers them in 6 cases.

## Why this package exists

P2-02's sign-off was **withdrawn** because its mechanism had no subject. The definition, the attenuation and `assertTokenPresented` were all complete and tested, and on every launched profile: nothing issued a token, nothing armed the requirement, no bundle mounted anything, and a spawned child received no token. must[1], must[3], acceptance[0] and acceptance[1] therefore had nothing to be true *of*.

A check that exists and is never armed is not a weaker version of a check that runs — it is a different fact, and the distinction is the whole reason this package is separate from the one that decides. Mounting this in `bundle/base` is what answers the third question: not "does the code exist" but "is it reached on a profile someone launches".

## What arming changes, and what it must not break

`requireForTools: true` makes a tool call that presents no token a refusal. The risk worth naming is not that refusal — it is the *unintended* one: a legitimate in-session call on a path that never attached a token would break while looking exactly like the feature working.

Two things guard that. `requireForTools` is a validated field rather than a constant, so a composition can mount the provider for issuance and audit before it enforces. And issuance is asynchronous in a way callers must respect:

`agent/session-start` is emitted synchronously and does not await its listeners, while issuing must persist the token before it can ever be revoked or audited. A tool call landing between session start and that durable write would hold no token yet. So the in-flight issuance is tracked, and a consumer presenting a token awaits **`whenSessionToken`**. `sessionToken` is the synchronous read for a caller that already knows issuance settled — using it on the presentation path would make the first tool call of a session intermittently refused.

## The signing key

The private key is generated by `createTrustKernel` into module-private state keyed by the signature-roots handle. This plugin holds only the **handle** and passes it through, so no key material reaches a config field, a log line, a session event, or this package's store. `tests/provider.spec.ts` asserts the written file contains no key rather than assuming it, because a future change that put the key on the handle would otherwise be invisible.

## Model Experience

No model-visible surface of its own: no tool, no prompt text, no session event. What a model can observe is indirect — with the requirement armed, a tool call that presents no token returns a refusal instead of a result. Token and KV-cache effects: none.

## Known Limitations and Deferred Work

- **Only the tools noun is armed here.** must[3] requires a token of tools, plugin RPC, external agents and ExecutionWorld. **Sub-agent delegation now derives**: `applyChildComposition` calls `deriveChild(parent, child, filter)` at the same point, and with the same filter, that narrows the child's tool VISIBILITY — so authority and visibility are decided together rather than one being enforced while the other is claimed. `subagent-spawn-in-process` and `ralph-loop` are its observation on launched profiles. The other three are recorded as readiness entries against their owners — BLOCKED-169 (P1-06, plugin RPC), BLOCKED-170 (P3-05, ExecutionWorld) and BLOCKED-171 (P5-07/08/09, external agents, which have no single owning epic).
- **The store is whole-state.** `CapabilityTokenStore` requires it: a revocation must become visible to the lineage check in the same instant as the digest that recorded it. That bounds how large a token set this provider is appropriate for, and a deployment issuing tokens at a rate where whole-state rewriting hurts wants a different provider behind the same definition.
- **The session-root token's resources track the tools visible in the agent's scope, and are re-signed when that set grows.** A single mint at session start is wrong on shipped compositions: `dsh-tool-subagent` — mounted twice in `bundle/base` — registers its tool from a `subagent/provider-added` listener and re-registers after an HMR provider swap, and installs per-agent scopes from `agent/created`. Any of those can land after the session's first tool call, and a token minted earlier would refuse that tool permanently. Re-issue is growth-only: a tool disappearing is not a revocation, and narrowing is delegation's job. Widening the root does not widen any child, because a delegated token is derived from it by subset. The cost is one signature per growth event, not per call. Widening via a wildcard is not the alternative: `resources` has exact-set semantics with no wildcard, and attenuation is a subset check, so a wildcard root would make every delegated narrowing meaningless.

- **A delegated child's root grows when the composition registers into its scope.** `attachStructuredRuntime` puts `structured_output` in the child's scope and Ralph's rounds require it, so a child can legitimately see a tool its parent never held; `resources` is an exact set and attenuation is subset-only, so the parent's root is widened to cover those names before the child re-derives. This is not an escalation of the parent: the token bounds AUTHORITY and the registry scope bounds VISIBILITY, and both hold at dispatch — a name the parent's scope cannot see is a name the parent still cannot call. Measured: without it the child is refused `structured_output` with `tool-not-in-scope` and `ralph-loop` loses its second round.
- **A detached run outliving its launcher is NOT yet answered.** The provider drops a session's token at `agent/disposed`, so a detached run re-attached after its launching session ended finds no parent to derive from. `spec/first100/exec/preflight-P4-09-detached.md` records the three readings and why the choice is security-visible; nothing here assumes one.

### Dev Note

<details>
<summary>Working context for maintainers — click to expand</summary>

This Dev Note is working context for maintainers: open questions and undecided directions. It is explicitly non-authoritative — shipped behavior and limits live in the sections above and in the package code.

Whether the session-root token should be re-issued when the tool registry changes is undecided. Today the resources are a snapshot at session start, which is correct for a fixed composition and wrong for one that registers tools mid-session; the alternative is a token per tool-call scope, which costs a signature per call.

`TOOL_CAPABILITY_VERB` is imported rather than written as `'call'`. That is deliberate and worth keeping: an issued token carrying any other verb is signed, recorded, and then refused at every call, which presents exactly as the gate working correctly.
