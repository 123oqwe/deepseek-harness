# Agent Note：对着陈旧构建刷新会删掉事件，而且什么都不会失败

Status: implemented

[English](2026-09-11-a-refresh-against-a-stale-build-deletes-events.md) | 中文

## 问题

`f4cb4beee8` 为已附着的宿主身份刷新了录制语料。同一次运行还从 `snapshots/sdk/` 中删掉了每一行 `run/task-profile`——共 34 行，覆盖全部 16 个场景。刷新运行的退出码是 0。没有任何门变红。语料被提交，损坏一直留在树里，直到后来一次全语料重放一次性报出 16 个 SDK 场景全红。

刷新会把运行**实际发出**的内容写回。因此一个运行没有发出的事件不会被保留——它会被删除。SDK 车道派生 `dsh --profile sdk`，执行的是构建产物 `lib/`；那次刷新发生时，`packages/run/run/lib/index.js` 仍早于 P4-02 U 的 `session.append('run/task-profile', …)`，直到将近两小时后才重建。子进程确实什么也没发出，写回便把这个"缺席"记录成了事实。

车道之间的分裂是让这件事可核查、而非只是一个说法的关键证据：同一次运行给 `snapshots/session/` **增加**了 90 行 `run/task-profile`，而 `snapshots/acp/` 一增一减持平。session 车道经 tsx 从源码启动，因此看见了新事件。只有跑构建产物的那条车道丢了它。

有两个性质让它不可见：

- **陈旧构建在写入路径上是无声的。** 在写回的那一刻，"产品不再发出该事件"与"构建早于该事件"没有任何区别；两者都表现为一次发出更少内容的运行。
- **被损坏的那条车道从未被回放校验。** 刷新按其构造必然重写并通过。只有随后的重放才做比较，而刚被重写的车道恰恰是没人再去复核的那一条。

## 决定

`assertBuiltArtifactsCurrent(packagesRoot, mode)` 在任一工作区包的 `lib/` 旧于其 `src/` 时，拒绝执行写回类运行。接入三条派生已发布 profile 的车道——`snapshots/sdk`、`snapshots/acp`、`snapshots/session`——挂在各自解析 mode 的位置。

有三个选择值得记录，因为每一个都决定了这道守卫能否真正抓住本次事故：

**检查是工作区全量的，不是车道局部的。** 删掉那些事件的产物属于 `packages/run/run`，而没有任何 SDK 场景提到这个包。派生 profile 会加载整张插件图，因此图中任何陈旧的包都可能改变运行发出的内容。一道只覆盖车道自身包的守卫会放行。

**逐包比较，而非整树比较。** 部分构建才是常态：一个包重建了，它的依赖没有。把全树的"最新 src"与"最新 lib"各取一个来比，恰好会掩盖这种情况。

**重放刻意不设防。** 重放只比较、从不写入，因此陈旧构建在那里会产生一个响亮的 diff——这正是暴露本次缺陷的信号。在重放处拒绝，只会把一个有用的失败变成一个环境错误。

## 影响

刷新现在会快速失败并点名陈旧的包，而不是提交一份变小的语料。代价是每次写回运行多走一遍 `packages/*/*/{src,lib}` 的目录遍历：293 个包、约 5300 个文件、约 0.13 秒。

它所属的一般规则是：**一个写回模式的可信度，不会高于它所观察的那个产物。** 当一个测试装置既生产又接受期望输出时，需要钉住的不是那次比较，而是被比较之物的来源。作为可执行的实践表述——刷新一条车道之后，回放它；那次重写 fixture 的运行，恰恰是唯一无法告诉你它们是否正确的运行。
