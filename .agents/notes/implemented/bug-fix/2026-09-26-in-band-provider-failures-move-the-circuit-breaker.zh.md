# Agent Note：在流中报告的 provider 失败也会移动断路器

Status: implemented

[English](2026-09-26-in-band-provider-failures-move-the-circuit-breaker.md) | 中文

## 问题

BLOCKED-347；P4-11 acceptance[2] 要求 provider 故障时断路器打开，并且可以恢复。`dsh-llm` 的运行时原先只让每条流的第一次 `iterator.next()` 经过断路器，而断路器只计抛出的失败。pi-ai 的流一旦开始就不再抛出：provider 的失败以一个 `usage` 块、随后一个 `error` finish 块的形式到达。于是第一次拉取正常返回，断路器把每次失败的调用都记为成功，在 pi-ai 路由上从不打开。lane A 的 A-498 量过（run 36223805295）：超过阈值之后，下一次调用仍然到达一个每次都失败的后端。

## 决定

- **断路器在流首次应答处判断。** 运行时在断路器的操作里拉取开头的那些块，一直拉到第一块不是 `usage` 的块，因为 `usage` 块说明不了端点有没有应答。
- **带内失败按抛出的失败判断。** 那一块是 `error` 或 `aborted` finish 时，操作抛出一个内部标记，携带该 finish 的失败；断路器用 `llmFailureFacts(failure)` 分类，这与它对抛出的失败经 `normalizeLlmFailure` 之后所用的函数相同。计不计由共用分类器决定：暂时性的码计入；请求本身有误、调用方一侧的情况（例如调用方自己的中止）以及无法分类的码都不计入。
- **流原样传下去。** 运行时接住自己的标记，产出适配器产出的那些块，包括 `usage` 块与 finish，因此消费方与 llm-retry 收到的与改动之前相同。
- **只在流首次应答处。** 在文本、推理或工具调用块之后到达的失败属于模型或传输，不移动断路器，与以前一样。

## 考虑过的替代方案

- **让 pi-ai 在产出任何内容之前把失败抛出。** 这会丢掉 pi-ai 随失败一起发送的 `usage` 块，而且流协议允许适配器在带内报告失败，断路器仍无法判断其他这样做的适配器。
- **不论在哪里到达，每个错误 finish 都计入。** 流中途的失败不能说明目的地宕了，这正是断路器只在流首次应答处判断的原因。

## 后果

- 在 pi-ai 路由上，一个每次调用都失败的 provider 在连续失败达到配置的次数之后会让断路器打开，下一次调用在到达后端之前就被拒绝。
- 不论有没有挂载断路器，以 `usage` 块开头的流都会等第一块其他的块到达后，才把这些 `usage` 块一起产出，而不是逐块产出。
- 验证：lane A 的 A-498，以及 `packages/llm/llm/tests/circuit-breaker-in-band.spec.ts`；后者还钉住了不计入的几种结果、流应答之后的失败，以及没有断路器时的流。
