# Agent Note：过期的会话令牌会重签，撤销的永不重签

Status: implemented

[English](2026-09-25-an-expired-session-token-is-re-issued-and-a-revoked-one-never-is.md) | 中文

## 问题

BLOCKED-331。会话令牌的寿命是 `sessionTokenTtlMs`（默认 24 小时），而提供方只在会话没有令牌、或其工具增加时才重签根令牌。于是会话活得比令牌长时，它照常运行，每个工具调用却都以过期被拒，也没有任何东西续签。委托令牌沿用父令牌的到期时间，到期后从不重新派生，attenuate 也不查父令牌是否已过期，所以父令牌过期后才起的子 agent 一出生就过期。`revokeSession` 把会话的令牌从内存里删掉，于是它的调用被拒的理由是「没有出示令牌」而不是「已撤销」；重启后的挂载还会给已撤销的会话签发一张新的根令牌。lane A 在出厂 headless profile 上量过根令牌、子 agent 与 workflow 三种情形（A-372、A-390、A-390b）。

## 决定

- **到期时在同一策略下重签，不结束会话**（delegate 的裁定）。`whenSessionToken` 每次被调用时都问：持有的令牌是否已过期。根令牌以相同的 subject、tenant、capability 与 verbs 重签，resources 按当时的注册表读取。委托令牌在同一过滤条件下，从父令牌当前的令牌重新派生；父令牌先续签。
- **每个会话同一时间只续签一次。** 某个会话的签发或重新派生尚未完成时，后来的调用方等待它，所以从同一个已过期父令牌并行重新派生的多个子 agent，只让父令牌续签一次，并都从这一张派生。
- **撤销是最终的。** `revokeSession` 之后，会话仍持有它那张已撤销的令牌，工具闸门以「已撤销」拒绝。`needsIssue` 与重新派生都跳过已撤销的令牌。签发根令牌或派生子令牌之前，先向持久记录查询该会话是否有令牌被撤销，紧挨在服务记录新令牌之前，所以重启后的挂载也不会再签发。已撤销的父令牌不再派生任何子令牌。
- **闸门先查撤销、再查过期。** 过期的令牌会续签，撤销的不会，所以既过期又已撤销的令牌仍以「已撤销」被拒。
- **`CapabilityTokenService.attenuate` 接收时间**，父令牌在该时间已过期时以 `parent-expired` 拒绝，所以不会签出一出生就过期的子令牌。时间是参数，与 `verify` 相同，服务层的用例就是这样注入时间的。
- **`run_code` 程序之内不续签，拒绝理由写明这一点。** 程序在整个运行期间出示启动它的那次 `run_code` 调用的令牌（`ptc.ts`），P2-05 的策略也按同一张令牌裁决程序的调用。在程序之内续签，会让调用出示的授权与策略裁决所依据的授权分开。程序发起的调用因过期被拒时，理由会指明是 run_code 程序，并说明下一次 `run_code` 调用会出示重签的令牌。

## 考虑过的其他做法

- **到期时结束会话并给出理由。** delegate 未采用：P2-02 没有任何条款要求这样做，而且这会把每个长时间运行的宿主都限制在 TTL 之内。
- **在程序之内重签。** 未采用，理由见上面的策略一条。
- **在 `attenuateToken` 里检查父令牌是否过期。** 未采用：这些判定函数不接收时间；服务为 `verify` 本来就接收时间。
- **仍在撤销时删除令牌，由闸门拒绝缺失的令牌。** 这是原来的行为：拒绝理由读作「没有出示令牌」，而且以后每一条新的签发路径都得记得不要重签。

## 后果

- 长时间运行的会话过了 TTL 仍能工作。每次重签记录一张根令牌，所以每个活跃会话每过一个 TTL，存储就多一张根令牌。
- 原生派发的一个步骤中，所有调用出示同一张令牌，所以在该令牌过期之后才开始的调用会以过期被拒；下一次派发会出示重签的令牌。
- 父会话已结束的委托会话，在令牌过期时无法重新派生，此后它的调用都以过期被拒。本包的 README 把这一点与 detached run 的限制记在一起。
- `CapabilityTokenService.attenuate` 新增必填的 `now`，`TokenAttenuationDenialReason` 新增 `parent-expired`。
- BLOCKED-330 的原生出厂组合用例改用已撤销的令牌来构造拒绝，因为 1 毫秒的 TTL 现在每次派发都会重签。
