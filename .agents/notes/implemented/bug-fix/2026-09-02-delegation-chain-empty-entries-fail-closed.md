# Agent Note: DelegationChain accessors fail closed on empty `entries`

Status: implemented

English | [中文](2026-09-02-delegation-chain-empty-entries-fail-closed.zh.md)

## Problem

`DelegationChain.entries` (`packages/identity/principal/src/types.ts`) is typed as a non-empty tuple (`readonly [DelegationEntry, ...DelegationEntry[]]`) so "no root" is unrepresentable — but that guarantee only binds a caller that actually went through `createChain`/`extendChain` (`packages/identity/principal/src/chain.ts`). Registry epic P2-01's Fault-stage ran real adversarial fault-testing against the already-hardened identity/tenant/admin core (`chain.ts`, `packages/core/agent-loop/src/runtime-context.ts`), constructing five real attack categories rather than reviewing code for plausible bugs: concurrency/TOCTOU on `resolveSessionIdentity`, cross-tenant confusion via a hand-built (non-`extendChain`) `DelegationChain`, the serialization boundary for non-admin tenant identity, delegation-depth/cyclic-chain resource exhaustion, and anonymous-dev admin-equivalence. Four were cleanly defeated by the existing design. The fifth found a real bug: `rootPrincipal` and the private `lastEntry` helper (which backs `currentPrincipal`/`currentTenantId`/`rootTenantId`) crashed with an opaque `TypeError` — `Cannot read properties of undefined (reading 'principal')` from `rootPrincipal`, `Reduce of empty array with no initial value` from `lastEntry` — on a `DelegationChain` whose `entries` is empty at runtime.

This is genuinely reachable, not a contrived unit-test-only input. `packages/core/session/src/chunk-rows.ts`'s `decodeStorageRecord` validates only chunk-row-tagged storage rows (`text-chunks`/`reasoning-chunks`/`tool-call-chunks`); its own doc states plainly that "every other value passes through as a single event, unvalidated." An `identity/attached` event (`SessionEventMap['identity/attached']`, `packages/core/session/src/types.ts:311`) is one such unvalidated value: a corrupted or hand-edited session-log line decodes straight through to `SessionEvent['data']['identity']` with no schema check on its `DelegationChain` shape. `lastAttachedIdentity` (`packages/core/agent-loop/src/runtime-context.ts`) reads exactly this value out of the session's event stream and hands it to `resolveSessionIdentity` as `recorded`; `ReactLoopAgent`'s constructor (`packages/core/agent-loop/src/agent.ts:115`) calls `resolveSessionIdentity(lastAttachedIdentity(session), options.identity)` directly in its body, with no guard between decode and this call. A malformed `entries: []` reaching either `recorded` or `supplied` therefore crashed agent construction itself with an opaque, undocumented failure instead of a clear, intentional rejection.

Proof method: mutation testing, not just a passing regression test. Reverting the fix (`git stash`-equivalent on the two-line `assertNonEmptyChain()` call sites) reproduces the exact opaque `TypeError`s in the new regression tests (RED); restoring the fix turns them GREEN — proving the tests actually exercise the crash path rather than passing vacuously.

## Decision

A new private helper, `assertNonEmptyChain(chain)` (`chain.ts`), throws one plain `Error` — `'invalid DelegationChain: entries is empty -- a chain must contain at least a root entry'` — when `chain.entries.length === 0`. `rootPrincipal` and the private `lastEntry` (shared by `currentPrincipal`, and transitively `currentTenantId`/`rootTenantId`) call it first, so every accessor that reads `entries[0]` or folds over `entries` fails with one clear, dedicated error instead of an accessor-specific crash. Both call sites gained a `@throws {Error}` JSDoc entry.

Regression coverage: `packages/identity/principal/tests/identity.spec.ts` proves `rootPrincipal`/`currentPrincipal`/`currentTenantId`/`rootTenantId` each throw the clear message (and explicitly `.not.toThrow(TypeError)`) on `{ entries: [] } as unknown as DelegationChain`, plus a control case confirming a well-formed chain is unaffected. `packages/core/agent-loop/tests/runtime-context.spec.ts` proves the fix is visible at `resolveSessionIdentity`'s own call boundary for both the `recorded` and `supplied` sides — the two inputs that actually originate from, respectively, session-log replay and a fresh caller.

## Alternatives considered

### Why not a named error class (matching `TenantMismatchError`/`ForgedPrincipalError`)?

Kept as a plain `Error`, deliberately, after weighing it against this file's own convention. `TenantMismatchError` and `ForgedPrincipalError` (`types.ts`) both represent adversarial, policy-level decisions: a hop or an agent id that is actively wrong according to a rule this package enforces, each carrying structured fields (`attemptedTenantId`/`actualTenantId`, `claimedPrincipalId`) a caller can branch on, and each has a legitimate reason a caller might want to catch and handle differently from an unrelated failure — a resumed session under a genuinely different tenant, a forged agent id to reject with a specific response. The empty-`entries` case is a different kind of failure: a broken data-structure invariant that the type system already claims is impossible, carrying no data beyond the message, with no legitimate handling path other than treating the whole `IdentityContext` as corrupt and refusing to proceed. A named class would invite exactly the kind of selective catch-and-branch the two policy errors are designed for, which is the wrong signal for a should-never-happen state that means upstream data is corrupt, not that a specific actor did something a security rule rejects. `assertNonEmptyChain`'s doc already used `@throws {Error}` when the F-stage fix first landed; this round confirms that was the right category rather than an oversight to correct. Rejected alternative: a new `EmptyDelegationChainError` class — it would carry no branchable data and no legitimate catch-and-handle path distinct from "this identity is corrupt," misrepresenting a should-never-happen invariant break as a normal policy outcome.

### Why the accessor layer (`rootPrincipal`/`currentPrincipal`/`currentTenantId`), not the session-log ingestion boundary (`decodeStorageRecord`)?

`decodeStorageRecord`'s own doc already discloses that it validates only the three chunk-row tags and passes every other value through unvalidated — a known, existing gap across the *entire* `SessionEvent` union, not something this fix introduces. Closing it for real would mean schema-validating every session event variant at decode time, or special-casing `identity/attached` alone at the session-storage layer — the latter would make `dsh-session`, a generic durable-log codec, reach into `dsh-principal`'s `DelegationChain` shape, a layering direction this package split (`chain.ts` pure logic vs. `packages/core/agent-loop` real wiring vs. `packages/core/session` storage) does not otherwise take. Either option is a `dsh-session`-scoped effort sized well beyond a `dsh-principal` fault-testing fix, and one this round did not attempt.

More decisively: the accessor-layer fix is required regardless of whether ingestion-boundary validation is ever added, because a hand-built `DelegationChain` object literal — the *other* attack vector this same fault-testing round constructed, independent of the session log — reaches `rootPrincipal`/`currentPrincipal` directly, bypassing `decodeStorageRecord` entirely. Validating only at ingestion would leave that vector open; validating at the accessor closes both at once, because it is the actual point where an invalid invariant would otherwise produce undefined behavior, regardless of how the invalid data arrived. Defense-in-depth at the ingestion boundary remains a legitimate future improvement to `dsh-session`'s own disclosed gap, but it is not additionally warranted here: it would not be a partial fix worth taking now (validating `identity/attached` alone while leaving the rest of the union unvalidated is inconsistent, not meaningfully safer), and the accessor-layer guard already provides complete, general protection for this specific invariant. Rejected alternative: add schema validation for `identity/attached` specifically at `decodeStorageRecord` — it would not close the hand-built-literal vector on its own and would be a partial (single-event-type) fix to a whole-union gap that is `dsh-session`'s to close, not worth taking in isolation.

**Return `undefined` from the accessors instead of throwing.** Not chosen: every caller (`extendChain`, `assertAgentDelegationValid`, `resolveSessionIdentity`, `assertRuntimeTenantPolicy`) treats the return value as always-present per the type; returning `undefined` would just move the opaque crash one call frame later, at a site with less context about which chain was invalid.

## Consequences

`rootPrincipal`/`currentPrincipal`/`currentTenantId`/`rootTenantId` now fail closed with one clear, greppable message on a structurally invalid chain, at the exact point invalid data would otherwise cause undefined behavior — proved by mutation testing (revert reproduces the original opaque crash; restore turns the new tests GREEN), not merely by a test that passes. This is an observable-behavior contract change on exported, cross-package-consumed functions: any caller currently relying on the crash's specific message/type (none found in this codebase) now sees a different, documented `Error` instead.

This fix-round Reviewer separately surfaced one new, non-blocking finding while re-attacking this fix: a hand-built chain whose root and terminal principals both match `recorded`'s tenant but whose intermediate hop carries a different tenant is not rejected by `assertRuntimeTenantPolicy`/`TenantMismatchError` (which only ever compare the terminal tenant), though it is still durably logged (`resolveSessionIdentity`'s `sameChainShape` check catches the per-entry shape difference, so `shouldLog: true`). This is disclosed in `chain.ts`'s `currentTenantId` doc as a companion to the existing root/terminal-endpoint framing, alongside a same-round verification that no real caller outside this package's own tests reads an intermediate chain entry today (`isInChain`/`assertInChain`/`assertAgentDelegationValid`), so it is a disclosed limitation rather than a live bug requiring a code fix.

The `decodeStorageRecord` "every other value passes through unvalidated" gap remains open for the full `SessionEvent` union, exactly as already disclosed in that function's own doc — this round neither closes nor further defers it; a future `dsh-session`-scoped effort to schema-validate the whole event union (or a specific high-value subset) is unaffected by anything decided here.
