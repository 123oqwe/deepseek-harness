# Agent Note: Plugin Manifest v2 real enforcement at profile boot

Status: implemented

English | [中文](2026-09-02-plugin-manifest-real-enforcement-at-profile-boot.zh.md)

## Problem

Epic P1-01's Contract and Provider stages built a complete, tested pure-function surface for Plugin Manifest v2 — schema validation, wildcard detection, the legacy `dsh.bundle` classification, and `compareDeclaredToObserved`/`decidePluginTrust` — but nothing in the codebase called any of it. No CLI read a fixture, no code walked a live Cordis `Context` to build the `ObservedPluginCapabilities` these functions compare against, and no boot path acted on a `'quarantined'` or denied decision. Acceptance[0] requires a missing manifest, a declared/observed mismatch, or a wildcard permission request to fail install or enter explicit quarantine at real profile boot, not just return a value nobody reads.

Provider-stage's independent Reviewer separately found that `compareDeclaredToObserved` compares by capability identity (name) only, never by field content, and filed this as a non-blocking Known Limitation specifically because no real enforcement existed yet to make it matter (BLOCKED-027). That ruling requires Usage-stage's Reviewer to re-judge the question against the real enforcement design this stage builds, not silently re-disclose it.

## Decision

Real observation, admission, and quarantine are wired at real profile boot, end to end:

- **`packages/host/plugin-inventory/src/index.ts`** adds the first real live-`Context` introspection in this codebase for per-plugin registrations: `buildObservedPluginCapabilities(ctx, rootFiber)` walks a plugin entry's Fiber subtree — the global Cordis `ReflectService` store (filtered by `Fiber.uid`, not `===`: a `Fiber` reached through a `Loader` `Entry.fiber` and one reached through a `ReflectService` `Impl` are not always the same object even when they name the same live fiber) for `ctxKeys`, `Fiber.getEffects()` label parsing for `toolNames`/`skillNames`/`eventNames`, and a live MCP-client entry's resolved `config.serverName` for `mcpServerNames`. `buildPluginPermissionStates(ctx, options)` composes that with each entry's own `package.json` `dsh` field (`classifyPluginDeclaration`) and, for a `'manifest-v2'` declaration, a real `compareDeclaredToObserved`/`decidePluginTrust` result.
- **`packages/plugin/plugin-manifest/src/index.ts`** adds `evaluatePreMountAdmission(declaration, production)`, the real pre-mount policy: `production: false` admits unconditionally (every existing profile keeps booting exactly as before); `true` denies a `'missing'`/`'legacy-untrusted'` declaration or a wildcard-requesting manifest before any of its code runs.
- **`packages/boot/app-boot/src/profile.ts`** adds `readPluginDeclaration`/`partitionProfileLayersByAdmission`, which classify and admit every bundle layer from its real on-disk `package.json`.
- **`apps/cli/src/profile-boot.ts`** wires both halves into the real boot sequence: `composeProfile` (now exported) calls `partitionProfileLayersByAdmission` before any patch reaches `boot()`, so a denied layer's patches never mount at all — the strongest form of enforcement, since the plugin's code never runs. After `boot()` settles, `applyPostMountPluginEnforcement(ctx, production, admittedLayerNames)` calls `buildPluginPermissionStates` and disposes the live Cordis fiber of any entry `decidePluginTrust` marked `'quarantined'` — real, not just decided. Both are gated by `resolvePluginEnforcementMode(process.env.DSH_PLUGIN_MANIFEST_ENFORCEMENT)`, mirroring `resolveFeatureGateEnvOverride`'s fail-loud validation (exactly `'enforce'` or unset; anything else throws).
- **`apps/cli/src/plugin.ts`** adds `runPluginVerify(fixturePath)`, the registry's own `pnpm plugin:verify <fixture>` — reads a fixture as a raw `dsh` field, classifies it, and reports `evaluatePreMountAdmission`'s real decision with exit code 0/1. Wired through a new top-level `plugin-verify` command (`apps/cli/src/args.ts`, `bin.ts`) rather than a `plugin` subcommand: Commander enforces a parent command's own `requiredOption` (`plugin --profile`) even for an invoked child subcommand that never uses it, and this check needs no profile. `package.json` gains `"plugin:verify": "node --import tsx/esm apps/cli/src/bin.ts plugin-verify"`.

**Enforcement defaults off.** No bundle package shipped in this installation declares a Manifest v2 yet, so `DSH_PLUGIN_MANIFEST_ENFORCEMENT=enforce` against a real profile today denies every one of that profile's bundles. The switch is real and tested against fixtures (`packages/plugin/plugin-manifest/tests/fixtures/*.json`, including three new malicious ones — `malicious-schema-spoof.json`, `malicious-mcp-elicitation.json`, `malicious-skill-secret-request.json` — and real boot-level proof in `apps/cli/tests/plugin-enforcement.spec.ts`), but no shipped profile can pass it on yet; that migration (adding real manifests to `dsh-base` and its dependents) is separate, later work.

**BLOCKED-027 re-judgment: ratified, not deferred again.** Building `buildObservedPluginCapabilities` for real confirms concretely that no live registration in this codebase carries `sideEffectClass`/`authAudience`/`allowedDestinations`/`dataClassification` — not `ToolDefinition` (`packages/core/tools`), not a Cordis service `Impl` (`vendor/cordis/src/reflect.ts`), not an MCP-client `Fiber.config`, not a `SkillDefinition` (`packages/skill/skill`). A field-content comparison would compare a declared value against a field that structurally does not exist on the observed side today — not a weaker check, but a vacuous one. The real gap is not closeable inside this epic's three packages; it needs a separate, larger change threading effect metadata through every tool/skill/MCP/event registration call site repo-wide. Identity-only comparison is therefore the real Usage-stage design, not a placeholder.

**Tool/skill effect labels gained the registered name.** `packages/core/tools/src/index.ts`'s `ToolRuntime.register` and `packages/skill/skill/src/index.ts`'s `Skills.register` each called `ctx.effect(fn, label)` with a fixed label (`'tools.register()'`/`'skills.register()'`), unlike `ctx.provide(name)`/`ctx.on(name)`'s own existing convention of embedding the name in the label. Both effect labels are now parameterized (`` `tools.register(${JSON.stringify(name)})` ``) — a minimal, behavior-preserving, precedent-matching change, and the only way to attribute a registered tool/skill name back to its owning fiber without a larger owner-tracking mechanism. Neither file's owner map entry exists (shared/unowned), so this carried zero owner conflict.

**No `pluginInventory` Remote method for permission states.** `buildPluginPermissionStates` was tried as a `@Remote('permissions')` method on `PluginInventoryGateway` and reverted after a real build failure: the typert Zod-schema emitter cannot serialize `PluginManifestV2`'s non-empty-tuple fields (`readonly [X, ...X[]]`, e.g. `CapabilityEffectDeclaration.authAudience`) — `TypertEmitError: tuple rest element must retain an array type`. It stays a plain function; `apps/cli` calls it directly for both the real CLI display and boot-time enforcement, satisfying acceptance[1] without needing the Remote surface.

## Alternatives considered

**Compare `Fiber` objects by `===` when building `ObservedPluginCapabilities`.** Rejected after failing in a real boot: a `Fiber` reached via a `Loader` `Entry.fiber` and the same live fiber reached via a `ReflectService` `Impl.fiber` are not reference-equal, confirmed empirically (`impl.fiber === entry.fiber` is `false`, `impl.fiber.uid === entry.fiber.uid` is `true`). `Fiber.uid` is the correct, stable identity.

**Fail the whole profile boot on any denied bundle layer, rather than excluding just that layer.** Not chosen: acceptance[0]'s "安装失败或进入明确 quarantine" (install fails or enters explicit quarantine) reads as two alternative outcomes, and excluding only the denied layer's patches is both a real "install failure" for that plugin specifically and lets the rest of a profile continue — the friendlier, more literally "quarantine" reading, and it produces a real, assertable boot-time difference (the denied plugin's Loader entries never appear) rather than an all-or-nothing crash.

**Thread effect metadata (`sideEffectClass` etc.) through every registration call site now, to close the BLOCKED-027 gap for real.** Rejected for this slice: touches `packages/core/tools`, `packages/skill/skill`, `packages/mcp/mcp-client`, and every other tool/skill/MCP/event registrar repo-wide — an epic-sized undertaking with its own blast radius, not a Usage-stage wiring job. The re-judgment documents this concretely rather than silently carrying the disclosure forward.

**Expose `buildPluginPermissionStates` as a `pluginInventory` Remote method.** Reverted after a real, reproduced build failure (typert cannot serialize `PluginManifestV2`'s non-empty tuples). Fixing the typert generator or designing a serialization-friendly `PluginPermissionState` projection is a separate concern from this epic's real-enforcement job.

## Consequences

A plugin with a missing/legacy manifest, a wildcard-requesting manifest, or a declared/observed capability mismatch is now genuinely denied or quarantined at real profile boot when `DSH_PLUGIN_MANIFEST_ENFORCEMENT=enforce` — proved end to end in `apps/cli/tests/plugin-enforcement.spec.ts` via real `boot()` calls, not mocked Loader state. `pnpm plugin:verify <fixture>` is a real, working command against every fixture the registry names, including the three new malicious ones. Tool-name collision — a second plugin registering a name the first already owns — was already real, tested enforcement in `packages/core/tools` (`ToolRuntime.register`'s `NamedEntries.insert` throwing on a duplicate) before this stage; nothing here duplicates that coverage.

The identity-only declared/observed comparison is now a confirmed, evidenced design decision, not a standing unexamined disclosure: no live registration in this codebase exposes the fields a field-content comparison would need. Enforcement itself is off by default in every real deployment until a later, separate migration gives at least one shipped bundle package a real Manifest v2 — this is disclosed in both package READMEs, not hidden behind the opt-in switch's mere existence.
