# Agent Note：workflow 运行等待审批

Status: implemented

[English](2026-10-04-a-workflow-run-waits-for-an-approval.md) | 中文

## 问题

Epic P2-07 的 must[2] 与 must[3] 要求运行能持久地等待审批，并在审批被判定后恢复，无论在同一进程里还是重启之后（acceptance[0]）；两次恢复相互竞争时，审批至多被消费一次（acceptance[1]）。U1 之后每项审批都经由持久队列，但只有回合里的工具调用会提出审批，而且它在自己的回合里等待；没有任何比进程活得更久的东西能够等待。

## 决定

- **由 workflow 运行等待（delegate 的裁定，方案 A）。** 脚本的 `await approval({ title })` 就是等待的调用，并且只有 detached 运行可以发起它：只有 detached 运行比启动它的回合活得更久，所以只有它能被唤醒。在别处这次调用抛出 `APPROVAL_UNAVAILABLE`，没有挂载审批存储时也一样。
- **等待记在运行日志里。** 宿主以运行自己的会话身份记录一项 run 范围的审批，在运行日志中记下提出它的调用的键、审批 id 以及记录它时所用的租户与主体，连同运行以什么启动，随后让运行以 `waiting_for_approval` 结算，交还它的 worker、租约与 agent。等待状态只存在于运行日志与存储中。
- **唤醒就是恢复。** 本进程里的 `approval-store/changed`，以及审批存储与 agent 注册表挂载后对本 home 运行日志的扫描，会在运行自己的会话中以运行日志记下的模型路由恢复它，取得它的租约，对账它的运行日志并重跑脚本。重跑到达同一次调用，由它以比较并交换消费审批，所以两次恢复至多一次越过这次调用继续。
- **由运行日志记下的查看者消费（D2）。** 审批以这次调用在运行日志中记下的租户与主体读取和消费，绝不以恢复它的进程的身份。
- **拒绝可以被捕获。** 被拒绝、被撤销、已过期或已被消费的审批抛出带 `refusal` 的 `ApprovalRefusedError`。它不是致命的 `WorkflowError`，所以脚本可以走另一个分支，而被请求的动作绝不会代它执行。
- **被唤醒的会话持有它原来持有的 token（D8）。** 在恢复运行的会话之前，`adoptDelegatedToken` 把为它记录的最新委派 token 交还给它，是同一个 token，所以它的范围与撤销谱系都不会改变。它绝不会被签发根 token，那会比启动方委派给它的更宽；token 已过期或已被撤销时，它什么也不持有，它的工具调用会被拒绝。
- **对模型不可见。** 不新增会话事件。模型用 `attach` 收取正在等待的运行时，读到的是一个指明该审批的错误。

## 考虑过的替代方案

- **由 agent Run 等待（方案 B）。** 它需要一个对模型可见的结果与后续消息、一条把审批绑定到单次调用的规则、Run 插件没有的唤醒 API，以及按会话划分的租约。
- **按需给被唤醒的会话签发 token。** 启动方已不在，provider 会签发根 token，比启动方委派的过滤范围更宽。
- **把等待状态也写进运行存储。** 那是运行日志已经持有的事实的第二份记录。

## 后果

- `WorkflowStopReason` 新增 `waiting_for_approval`，每个穷举它的消费方都处理它；tool-workflow 只记录前台运行的结束，而前台运行从不等待。
- 过期的审批，或另一个进程在共享存储中判定的审批，只在下次扫描时唤醒它的运行。
- `approvalWaitMs`（默认一天）不应长于会话 token 的寿命：token 过期之后才被唤醒的运行什么也不持有。
