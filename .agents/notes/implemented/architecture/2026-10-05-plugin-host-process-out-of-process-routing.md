# Agent Note: A third-party plugin layer is routed out of the in-process tree and run in its own process

Status: implemented

## Problem

Epic P1-06 slice 1 built the capability-scoped RPC seam (`@deepseek-ai/dsh-plugin-host-rpc`) and slice 2's package (`@deepseek-ai/dsh-plugin-host-process`) spawns one plugin in a subprocess, but nothing yet ROUTED a real profile's layer to it: every admitted bundle layer still mounted its patches into the host's one in-process cordis tree with the real `ctx`, and the manifest's `executionMode` (`in-process|worker-thread|process|container`) was validated with no routing consumer. Slice 2 "part 2" has to make the boot actually divert a layer out of the in-process tree and run it out-of-process, and it has to do so for the layer the capability model most needs isolated — a third-party plugin — without trusting that plugin to classify itself.

A second problem surfaced while wiring it: `spawnPluginHost` as slice 1 shaped it wanted `principal` + `capability` at attach time, but the host is spawned once at app `boot()` where there is no session, principal, or capability — those are per-dispatch concepts minted in the agent loop.

## Decision

Routing lives in `apps/cli/src/profile-boot.ts` `composeProfile`, co-located with the admission/compose authority. Each admitted layer is classified: a layer that is NOT the installation's own copy — `isInstallationOwnLayer(layer, anchor)` (`packageDirFromAnchor(anchor, name) === layer.packageDir`, the trusted-identity discriminator newly exported from `@deepseek-ai/dsh-app-boot`, the same check `installationWildcardGrants` uses) — is third-party and routes out-of-process REGARDLESS of what its own untrusted manifest claims (fail-safe); a trusted layer routes out-of-process only when its manifest declares `executionMode: 'process'`. Out-of-process layers' patches are excluded from `bundlePatches` and their names from `admittedLayerNames`/`bundleLayers`, so the in-process mount, `warnUnsignedDevPlugins`, and post-mount quarantine only ever see genuine in-process Loader entries; the routed layers are recorded in a new `ComposedProfile.outOfProcessLayers`. `boot()` spawns each via `spawnPluginHost` after the in-process tree mounts (so the host's `subprocess` and `tools` services exist), sourcing the declared tool names and manifest digest (`computeManifestDigest`) from the layer's TRUSTED installed manifest (`classifyPluginDeclaration` → the v2 manifest), never from the plugin; disposers are revoked and children terminated on shutdown.

The host is app-level (one process reused across the app's sessions), so `spawnPluginHost` / `attachPluginRpcHost` carry only static plugin config — `principal`/`capability` are removed from their options. Instead `registration-consumer.ts` stamps each `tool.invoke` with the REAL dispatch's authority sourced from `exec.capabilityToken` (P2-02 must[3], the per-dispatch token the capability gate already checked): `principal = token.subject`, `capability` = a digest view built from the existing `digestToken`, deadline = the token's `expiresAtMs`. A dispatch presenting no capability token is refused — the app-level host holds no ambient authority of its own.

## Consequences

Part 2 is pure routing with no host-process environment change: the child's zero-ambient context already comes from existing infrastructure — `child-runtime` builds a bare `Context` exposing only a `tools` forwarding stub (no `trustKernel`, `fs`, `subprocess`, …), and the subprocess provider's default child environment (`scrubbedParentEnv`) already strips `DSH_*` and credential variables. A trusted layer declaring `worker-thread` or `container` is NOT handled by this slice (those are other execution worlds, P3-09) and stays in-process for now. apps/cli gains a direct dependency on `plugin-host-process` and `plugin-host-rpc` (four-manifest wiring).

Known Limitation — process-first, not OS confinement: this isolates the host's in-process CAPABILITIES from the plugin (process boundary + capability-scoped RPC + scrubbed environment), but does NOT confine the child at the OS level — it can still make raw filesystem/network syscalls under the user's identity. OS confinement (sandbox / microVM) is P3-12 must[2] / P3-09, a separate execution world.

Testing: the delegate-authored blind red-first `tests/first100/fixtures/P1-06.slice2-out-of-process-routing.rf{1,2,3}` boots a real profile through `runProfile` → `composeProfile` under `runLoaderSmoke`, admits third-party layers, and asserts RF1 the plugin's reported pid ≠ host pid, RF2 `reachableForbiddenServices` and visible `DSH_*` env are both empty, RF3 a third-party layer that CLAIMS `executionMode:'in-process'` is still routed out-of-process (fail-safe). All three were confirmed genuine-red in-process before this change and turn green after it. The per-call-authority revision of slice 1 carries its own red-first.

## Alternatives considered

- **Fixed app-level identity on the host (option B).** Stamp one app principal + app-lifetime deadline on every plugin invoke. Rejected: a fixed, non-expiring authority defeats the per-dispatch capability-token model (P2-02) and invents a new app-level capability source. The stamped token IS the authority; host-side enforcement per calling session does not cure an over-broad wire token.
- **Per-session plugin host (option A).** Spawn one host per session and bind its capability at attach. Rejected: capability is minted per-dispatch, so an attach-bound token is coarser/staler than the current grant; it also needs a new session-lifecycle spawn hook and adds per-session isolation today's in-process design does not have (scope creep vs process-first).
- **Classify routing inside `negotiateProfileLayerCompatibility`.** Rejected: that step does compatibility partitioning only; routing is co-located with `composeProfile`, the authority that builds the boot tree and already holds the install anchor and each layer's identity.
