# Agent Note: Feature-gate mechanism wiring before any real gate exists

Status: implemented

English | [中文](2026-09-01-feature-gate-mechanism-wiring-before-any-real-gate.zh.md)

## Problem

Epic P0-05's Provider-stage (`@deepseek-ai/dsh-feature-gates`) built real, pure `resolveFeatureGate`/`evaluateFeatureGate`/`checkFeatureGateExpiry` functions, but nothing in the codebase called them: `--dump-config` (must[3], "must show the final resolved gate's source and full override chain") did not render feature gates at all, and no gate declaration's expiry was checked anywhere in the release pipeline (acceptance[2], "an expired gate fails in the release gate"). Epic P0-05's own nonGoals forbid declaring a real capability gate here ("不引入与本项无关的垂直业务逻辑" — no vertical business logic unrelated to this item) and this repository has no capability that has actually migrated behind a gate yet, so the U-stage wiring had to be real and testable while declaring nothing.

## Decision

- **Shared resolver, not a duplicated computation.** `apps/cli/src/profile-boot.ts` gains `FEATURE_GATE_DECLARATIONS` (empty), `featureGateEnvVarName`/`resolveFeatureGateEnvOverride` (the real `env` override-chain layer, `DSH_FEATURE_GATE_<ID>`), and `resolveProfileFeatureGates(profile, declarations, env)`. `apps/cli/src/dump-config.ts`'s new `renderFeatureGateDump` and `runProfile`'s boot both call this one function, so `--dump-config` and a real boot agree on the same profile/environment.
- **No new Cordis Context service augmentation.** `runProfile` provides the resolved gates with a bare `hostCtx.provide('featureGates', resolveProfileFeatureGates(options.profile))`, not a `declare module '@deepseek-ai/cordis' { interface Context { featureGates: ... } }` block. Every existing service augmentation in this repository (grepped exhaustively) lives in the capability-owning package's own `src/index.ts` — `dsh-trust-kernel`, `dsh-launch-environment`, `dsh-cmdline`, etc. — never in `apps/cli`. The owning package here, `packages/migration/feature-gates`, is outside this epic's declared U-stage `files[]` (only `profile-boot.ts`/`dump-config.ts`/`cordis.patch.yml`). Cordis's own `ReflectService` already types `get(name: string, strict?: boolean): any` and `provide(name: string, value?: any): () => void` as explicit overloads "for service names outside the typed Context surface" (`vendor/cordis/src/reflect.ts`), so this is a supported, not a hacky, escape hatch. The typed surface is deferred to whichever future epic registers the first real gate.
- **No new `cordis.patch.yml` row.** Read the whole file: every row mounts a real Cordis plugin. Feature gates, like the Trust Kernel (Epic P0-02), are a non-plugin boot-time mechanism with no capability of their own to mount — `pinTrustKernel` similarly has no row there.
- **acceptance[2] wired into the repository's real release gate, not P0-07's evidence collector or this program's own ledger.** `scripts/release/verify.ts` (`pnpm run release:verify`) is the pre-existing, genuine release gate this repository already runs from GitHub Actions for every `dsh`-family release; its `verifyVersions` step already guarantees one shared version across every `dsh` member, exactly the harness-version scheme `FeatureGateDeclaration.removalVersion` is defined against. A new `scripts/release/feature-gate-expiry.ts` exports `assertNoExpiredFeatureGates` (reusing `checkFeatureGateExpiry`, not reimplementing it) and its own `RELEASE_GATE_FEATURE_GATES` (also empty), wired into `verify.ts`'s `main()` for the `dsh` family only.
- **Two separate empty declaration lists, not one shared one.** `apps/cli/src/profile-boot.ts`'s `FEATURE_GATE_DECLARATIONS` and `scripts/release/feature-gate-expiry.ts`'s `RELEASE_GATE_FEATURE_GATES` are not the same array. `apps/cli` (`@deepseek-ai/dsh`) is a bin-only package (`"exports": null` in its `package.json`, enforced by `scripts/verify-application-entrypoints.ts`), so nothing outside it can import from its `src/`; this repository's own convention requires cross-package imports to go through a package name, never a relative path across a package boundary (`AGENTS.md`: "Use package names across packages and .ts in local relative imports"). A future epic that declares a real capability gate registers it in both lists.

## Alternatives considered

**Add the `declare module '@deepseek-ai/cordis'` augmentation now, inside `apps/cli/src/profile-boot.ts`.** Rejected: no other service augmentation in the repository lives outside its owning capability package, and the real owner (`dsh-feature-gates`) is out of this epic's declared U-stage scope; adding it there without a real consumer would be exactly the kind of production-shaped machinery this epic's nonGoals warn against.

**Give `apps/cli` a package export for `profile-boot.ts` so `scripts/release/verify.ts` could import its declared-gates list directly.** Rejected: `apps/cli` is deliberately bin-only — `docs/architecture.md`'s Application-launch rule forbids "public SDK argv escapes," and adding an export surface only to share one empty array is disproportionate machinery for a mechanism with no real gate yet.

**Wire acceptance[2] into `scripts/release/collect-evidence.mjs`/`verify-evidence.mjs` (Epic P0-07, same wave).** Rejected: that mechanism verifies a first100-registry gate command's captured output (log/artifact digests) — a different domain from a feature gate's version lifecycle. Coupling them would read as scope creep past this epic's own boundary, not a natural integration.

## Consequences

`pnpm dsh --profile <name> --dump-config` and `pnpm run release:verify --family dsh` both run the real mechanism today, but print/check nothing new: both declared-gates lists are empty, matching this repository's actual state (no capability has migrated behind a gate). The wiring itself is proven end to end with synthetic test declarations: `apps/cli/tests/feature-gate-boot.spec.ts` boots a real Cordis Loader composition (mirroring `packages/kernel/trust-kernel/tests/boot.spec.ts`'s pattern) proving a mounted plugin can read `ctx.get('featureGates')`; `apps/cli/tests/dump-config-feature-gates.spec.ts` proves `renderFeatureGateDump`'s exact per-row provenance output; `scripts/release/feature-gate-expiry.spec.ts` proves `assertNoExpiredFeatureGates` fails, naming every expired gate, against a synthetic expired declaration.
