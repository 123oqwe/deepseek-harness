# preFlight — P2-06 C (审批绑定完整规范化参数、资源与前置状态,Contract 阶段)

Written 2026-09-12 by lane B at `c281554e88`, branch `lane-b-p2-06`. Table first. This page continues `preflight-P2-06.md` and does not restate its two rulings; it answers the two items that page left as **C-stage measurements**, and states what C decides, builds, and how each piece fails if built wrong.

## The two measurements that page deferred

**Item 3 — can an `ApprovalRequest` reach a `Principal`? Yes, transitively, and the shape matters.** `ApprovalRequestEvent` (`packages/interaction/user-approval/src/types.ts:66-95`) carries `agent: Agent`, and `Agent.identity?: IdentityContext` (`packages/core/agent/src/types.ts:28`) carries the acting principal and its full delegation chain. So the request **already reaches** the principal — but through an **optional** field on a different package's type, not as a field of its own. That is the whole content of acceptance[0]'s "切换账户" half: binding must capture the principal AT ASK TIME and re-verification must compare against it, because an `Agent` re-read at execution time reports whoever is acting THEN, which is exactly the substitution the clause forbids.

**Item 4 — does a batch approval path exist? No.** `approval.request` takes one request; the five production askers are `core/tools/src/index.ts:2246`, `core/tools/src/external-effect.ts:418`, `context/agent-instructions/src/index.ts:88`, `workspace/command-workspace-trust/src/index.ts:67`, and `sandbox/sandbox/src/escalation.ts:173`, each with a single subject. `batch` appears nowhere in `user-approval`'s sources. **So the ACP guard (`callId === undefined → next()`, `acp/src/index.ts:157`) cannot interact with a batch that does not exist**, and validation[1]'s "batch mutation" test has no production subject today. Declared here rather than discovered at the F stage: a batch case would have to construct the batch it tests, which makes it a test of a thing this harness does not do.

## What C decides, what C builds, and how each fails if built wrong

| clause | C already decides | C must build | how it fails if built wrong |
|---|---|---|---|
| **acceptance[0]** approval survives no substitution of parameters, account, or file/object version | P2-03's canonical form and `computeArgumentsHash` (`action-manifest/src/canonicalize.ts:133`) are frozen and reused — C writes NO canonicalizer (ruling 2) | `ApprovalBinding`: the manifest digest, the arguments hash, the acting principal, the declared preconditions, the capability-token digest and the policy version, captured at ask time; plus `verifyApprovalBinding(binding, now)` deciding `valid` or a named mismatch | **The failure mode is a binding that re-reads instead of comparing.** A verifier that resolves the principal from the live `Agent`, or re-hashes the arguments it is handed rather than the ones the decider saw, passes every test written against it and defeats the clause completely: substitution changes the live value and the verifier moves with it. The C cases must therefore hold a RECORDED value against a CHANGED one, never a value against itself |
| **acceptance[1]** sensitive values may display redacted, but the hash still covers the real canonical value | `redactTokenForLog`'s precedent (P2-02) — a redacted projection is what crosses a boundary, and the digest stays over the real value | A `redacted` VIEW beside the binding, not instead of it: the six display fields as the decider sees them, with the digest computed over the unredacted canonical form | **The failure mode is redacting before hashing.** If the view is produced first and the digest taken over it, two different real arguments that redact identically get one approval, and the clause is inverted: the hash would cover what was shown instead of what will run. A case must show a pair that DISPLAYS identically and BINDS differently |
| **acceptance[2]** the approval event and the final action reference each other one-to-one | `approval/asked` + `approval/decided` already exist as an enclosed pair, refused outside an open turn (`user-approval/src/index.ts:237`) | The reference itself: the binding carries the manifest's `actionId` and idempotency key, so an action names exactly one approval and an approval names exactly one action | **The failure mode is a reference that is one-to-many in one direction.** If the binding names the action but the action carries nothing back, "从 action 反查唯一 approval" (validation[2]) is answerable only by scanning, and two approvals for one action become indistinguishable from one. A case must fail when a second approval is minted for the same action |

**must[1] and must[2] are the same decision seen twice, and C states it once.** must[1] re-verifies digest, preconditions, capability token and policy version before execution; must[2] says any field change invalidates the approval and forces a new request. So the verifier's refusal reasons ARE must[2]'s enumeration: one reason per bound field, closed, and a refusal names WHICH field moved. A boolean verifier would satisfy neither clause observably — an operator cannot act on `false`.

## What C does NOT do

- **No rendering.** Ruling (1) put the six display fields in scope for the EPIC, and the answerers are U-stage subjects. C decides what the fields ARE and what the digest covers; a C case asserting an ACP payload would be proving the U stage's clause early and against a fake surface.
- **No canonicalizer, and no re-proof of one.** Key ordering, number spelling and NFC/NFD are P2-03's frozen cases. A C case here re-asserting them would be proving another epic's clause.
- **No new `Principal` plumbing.** The principal is reachable through `Agent.identity` today; whether the binding should carry it directly or dereference at ask time is C's decision to make, but adding a field to `Agent` is not in this stage.

## Open, and named rather than assumed

1. **`identity` is OPTIONAL on `Agent`.** An agent with none binds no principal, and the honest options are refusing the ask or binding "no principal attached" as a value. I lean to the second — a value a policy can match on, the same argument `ExecutionWorldFact`'s `absent` won — but it is a decision, and a C case must pin whichever is chosen.
2. **Where the binding lives.** The registry declares `packages/interaction/user-approval/src/canonical.ts` as the C-stage `N` file. Ruling (2) already changed what that file IS; whether the verifier lives beside it or in `index.ts` is not settled here.
3. **Validity period (must[0]'s sixth field) has no clock owner yet.** An expiry is meaningless without deciding whose clock measures it and what happens to an in-flight execution when it lapses mid-dispatch. C can define the field and the comparison; the dispatch-time behaviour belongs to U.
